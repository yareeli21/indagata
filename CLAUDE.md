# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Indagata manages and queries educational research instruments (encuestas, entrevistas, pruebas estandarizadas). A researcher uploads an instrument, the author approves its Dublin Core and type-specific metadata, KPIs get suggested through semantic similarity and accepted, and the approved instrument is then indexed into ChromaDB for a RAG chat and KPI dashboards. Code, identifiers, routes, UI text and docs are all in **Spanish**, so keep new code in Spanish too.

## Running things

The local Python venv lives at the repo root: `.venv\Scripts\python.exe` (some machines name it `venv\`; install test deps with `.venv\Scripts\python.exe -m pip install -r requirements-dev.txt`; it skips torch because the tests fake embeddings). The shell is PowerShell, so chain commands with `;`, not `&&`, and use `curl.exe`, not the `curl` alias.

```powershell
docker compose up -d                              # whole stack
docker compose up -d --build <service>            # rebuild one service after dependency/Dockerfile changes
docker compose logs -f <service>
docker compose up -d postgres                     # DB only, then run a service locally:
cd services/<service>; uvicorn main:app --reload --port <port>
```

Source is bind-mounted into the containers (`./services/<svc>:/app`, `./shared:/app/shared`), but the services start uvicorn **without** `--reload`. After a code change, run `docker compose restart <service>`. Use `--build` only when requirements change.

**Tests** use pytest. Run them per service, from inside the service folder, because each `tests/conftest.py` puts its own service dir plus the repo root on `sys.path`:

```powershell
cd services/storage-service; ..\..\.venv\Scripts\python.exe -m pytest tests
..\..\.venv\Scripts\python.exe -m pytest tests/test_indice.py::test_nombre -q   # single test
```

Do not run pytest across several services in one process. The flat-layout services all have top-level modules named `main`, `models`, `dependencies` and `services`, and those collide. The test suites use SQLite in memory with `tt_rag` ATTACHed as a schema, with JSONB compiled to JSON, plus in-memory fakes for Chroma and embeddings. They need no Postgres, Chroma or Ollama. Services with tests: cleaning, knowledge, storage, metadata, visualization and analysis. `analysis-service` has an extra `requirements-dev.txt`.

**Frontend** (`pixel-perfect-pixel/`, TanStack Start + Vite + React 19 + Tailwind 4 + shadcn/Radix):
```powershell
cd pixel-perfect-pixel; npm run dev    # also: npm run build, npm run lint, npm run format
```
`src/routeTree.gen.ts` is generated by the TanStack router plugin, so never hand-edit it.

**KPI seed**: `python scripts/seed_kpis.py`, run from `services/analysis-service` (or inside its container). It reads `infrastructure/postgres/seed/KPI_Ampliacion.csv` into `tt_rag.kpi` (`TRUNCATE … CASCADE`, which also wipes accepted KPIs in `kpi_inferido`); then `POST /vectorizacion/kpis/reindex` (analysis-service, needs a JWT) re-embeds the `kpis` Chroma collection. It also loads `seed/KPI_Fuentes.csv` (verified reference sources per KPI, linked by exact KPI name) into `tt_rag.kpi_fuente`; `python scripts/seed_kpis.py --solo-fuentes` reloads only the sources without touching the catalog or accepted KPIs. Only add sources whose URL you have checked.

## Architecture

### Microservices + `shared/`
Seven FastAPI services live under `services/`. They share one Postgres database (schema `tt_rag`) and one Python package, `shared/`:
- `shared/db/core/config.py`: a single pydantic-settings `settings` object for every service. It reads the root `.env`. Defaults target localhost, and docker-compose overrides them with container hostnames. Storage paths are resolved relative to the repo root.
- `shared/models/` (SQLAlchemy ORM) and `shared/schemas/` (Pydantic DTOs) mirror `infrastructure/postgres/init/01_schema.sql` 1:1. **The SQL file is the source of truth**: when they disagree, fix the model, never the SQL.
- `shared/auth/`: JWT creation and validation (`crear_access_token`), password hashing, roles (`investigador`, `administrador`), and **service tokens** (`crear_token_servicio`) for service-to-service calls.

`import shared` resolves differently depending on where the service runs. In Docker, `shared/` is copied or mounted to `/app/shared`. Locally, each `main.py` adds the repo root to `sys.path` when `./shared` is missing. Copy that shim into any new service.

Two service layouts coexist:
- `app/` package (`instrument-service`, `analysis-service`, `api-gateway`): `app/routers`, `app/services`, `app/schemas`…
- Flat (`metadata-service`, `storage-service`, `visualization-service`, `cleaning-service`): top-level `routers/`, `services/`, `models.py` (HTTP DTOs) and `dependencies.py`.

Every service follows the same layering: routers → `dependencies` (typed `Annotated` deps such as `DBSession`, `Investigador`) → services → `shared` models.

### Auth
`api-gateway` issues the JWT (`POST /auth/login`, `/auth/me`, `/auth/register` for admins only). Every service validates it with the **same `SECRET_KEY`**, so a mismatch shows up as a 401. The token expires after 60 minutes. Dev users seeded by `infrastructure/postgres/init/05_seed_usuarios.sql` are `admin@indagata.com` / `admin123` and `investigador@indagata.com` / `investigador123`. In TestClient tests, bypass auth by overriding `get_current_user` / `get_db` through `app.dependency_overrides`.

### Gateway proxy
`services/api-gateway/proxy/proxy.py` forwards the path **unchanged** by prefix, with no renaming and no response wrapping. Status codes and bodies pass straight through. It keeps `Authorization` and passes back `Content-Disposition`, `X-Checksum-SHA256` and `X-Nombre-Archivo`.
`/instrumentos/*` → instrument, `/api/metadata/*` and `/api/enrichment/*` → metadata, `/visualizacion/*` and `/rag/*` → visualization (`/rag/chat` streams SSE; `GET /rag/*` serves the metrics; `PUT /rag/*` saves the human rating), `/limpieza/*` → cleaning, `/conocimiento/*` → knowledge, `/almacenamiento/*` → storage (admins only).
Every prefix registers both a base route and a `{path:path}` route on purpose, to avoid FastAPI's 307 redirect. When you add a new upstream prefix, follow the same pattern.

### Instrument lifecycle (data flow)
The canonical instrument id across services and the frontend is **`id_crudo`** (the PK of `raw_data`).
1. **instrument-service** `POST /instrumentos/upload`: detects the file type and parses it into a tabular or document form (`app/parsing/`), then hands the raw bytes to storage-service. The storage backend is a port with `http` and `local` implementations, chosen by `STORAGE_BACKEND`.
1b. **cleaning-service** `/limpieza/{id}/ejecuciones` (wizard step «Limpieza»): automatic phase per type (survey / interview / standardized test), assisted phase where the researcher decides the findings, then `confirmar` writes the clean CSV (`;`, UTF-8 BOM) to storage-service as a `clean` artifact and the `reporte_limpieza` JSONB to `tt_rag.limpieza_ejecucion` (one row per version). It sets `instrumento_procesado.ruta_de_archivo_limpio`. Editable rules live in `services/cleaning-service/config/*.yaml`. After saving, `GET /limpieza/{id}/resumen` returns the statistics of the latest confirmed cleaning plus analysis suggestions (`shared/conocimiento/sugerencias.py`, thresholds from `documentación/02_Desarrollo.md §X.7.2`), without sample rows; the author/admin always, other researchers once the instrument is approved. The catalog quick view shows it («Calidad de los datos y sugerencias de análisis»).
2. **metadata-service** `/api/metadata/{id}/propuesta` proposes Dublin Core (13 fields) using heuristics, from the **latest confirmed cleaning** (clean CSV + report, `services/desde_limpieza.py`). New instruments without a confirmed cleaning get a 409; instruments standardized before the cleaning step still use the raw file (`METADATA_EXIGIR_LIMPIEZA` toggles the requirement). When `METADATA_USAR_LLM` is on, Ollama fills the interpretive fields and degrades gracefully if it is unavailable. `/vista-previa` previews the standardized JSON without saving. `/aprobar` (author or admin) persists `metadatos_dc` and `metadatos_enriquecidos_*`, saves the standardized JSON through storage-service, and triggers RAG ingestion.
2b. **knowledge-service** `/conocimiento/{id}/perfil` builds the **perfil semántico** (Dublin Core + type metadata + questions; the only thing embedded to associate KPIs) in `tt_rag.version_conocimiento` (one row per version: `perfil_aprobado → kpis_confirmados → borrador → vigente`). `/documento` builds the **documento final** per type (interpreted answers per respondent, precomputed summaries, accepted KPIs; validated with JSON Schema in `esquemas/`) and stores it in storage-service as a `documento` artifact. `/documento/{v}/publicar` makes it `vigente`, rewrites its long-format rows in `tt_rag.respuesta_interpretada`, and asks storage-service to re-ingest in the background (`BackgroundTasks`; embedding hundreds of respondents takes minutes on CPU).
3. **analysis-service** `/vectorizacion/perfil/propuestas` and `/confirmar` associate KPIs by units of the perfil semántico (score = 0.45·general + 0.45·questions + 0.10·coverage, LLM justification with template fallback). The older `/vectorizacion/propuestas` (summary-based) still exists. metadata-service `/finalizar` adds the accepted KPIs to the technical JSON.
4. **storage-service** owns **all** file storage and is the **only writer** of the Chroma `instrumentos` collection and of `documento_vectorizado`. Artifacts use versioned keys `<tipo>/<id>/<versión>__<nombre>` with a SHA-256 hash that is checked on download. Ingestion uses the **documento final vigente** when there is one (`services/chunks_documento.py`) and falls back to the technical JSON otherwise. It ingests only author-approved instruments and sets `estado = vectorizado`.
5. **visualization-service** is read-only over the database and Chroma, except for writes to `rag_log`. It serves the catalog with facets, the KPI dashboards ("which questions measure a KPI" = nearest `pregunta` chunks to the KPI vector), related instruments, downloads (raw/json/`.sav` export through SPSS) and the RAG chat (see below).

### RAG chat (visualization-service)
**Chunks** (storage-service, `chunks_documento.py`, `VENTANA = 450` / `SOLAPE = 80` characters because the embedding model only reads ~128 tokens). From the documento final: survey → ficha (`encabezado`, always chunk 0), one `pregunta` per question with its summary, one or more `respondente` per person (context + answers by **meaning**, never codes; lists packed by whole lines), one `kpi` per accepted KPI with justification and evidence; test → `reactivo` (answer distribution, most chosen option; tests are never graded), `alumno`; interview → `pregunta` guide and one `intercambio` per question-answer pair. Metadata: `instrumentoId`, `tipo`, `seccion`, `preguntaId`, `respondenteId`, `kpiId`, `fuente` (`documento` | `json_tecnico`). Display IDs are short (`R017`, `p04`, `E02`); metadata keeps the full ones (`INS-0012-R017`). Re-ingest published instruments with `docker compose exec knowledge-service python scripts/poblar_respuestas.py` (also fills `respuesta_interpretada`).

**Pipeline** (`services/rag_service.py → planear()`):
1. **Domain rules** (`services/dominio.py`, editable `config/dominio.yaml`): privacy (re-identification), manipulation (ignore rules / show prompt) and out-of-domain tasks (poems, recipes, translations…) get a fixed message with no LLM call.
2. **Platform help** (`config/ayuda.yaml`): usage questions are answered only from that curated base and cited as `[Ayuda: …]`; no Chroma query.
2a. **Follow-ups of inference** (`services/seguimiento.py`, 10 nov): with history, a question that reasons about the previous answer («¿por qué crees que pasa eso?», «¿qué podría hacer la universidad?», «¿quién lo dijo?»; not «¿cuántos…?», IDs or a new long topic) is answered from that answer's own evidence read from `rag_log` (its source cards with passages and its computed result), skipping interpretation; the model presents inferences as interpretation and may only name the IDs present in the evidence. «¿Qué significa eso?» right after a computed answer is deferred: if `_retomar_anterior` re-runs the previous plan that wins, otherwise the follow-up answers.
2b. **Interpretation → execution** (`RAG_INTERPRETACION_LLM`, redesign of 28 oct; `services/consulta_planificada.py`): Ollama turns the question + last 4 messages (`ChatRequest.historial`) + a compact catalog of each instrument (`catalogo.py`) into ONE JSON plan (`plan_consulta.py`, schema in `esquemas/plan_consulta.json`, 12 intents), validated against the catalog and anchored to what the question says literally (`anclaje.py`). Structured intents run in `ejecutor.py` (deterministic: filter/count/order/limit/group; findings from `hallazgos.py`); since 4 nov every structured result is also complemented by **RAG retrieval** (`rag_service._apoyo_rag`: the closest Chroma fragments of the same instrument, filtered to the result's respondents or the computed findings' questions; in interviews the retrieved exchanges' questions are added to the person's table and findings come from the retrieved text), so the model gets RESULTADO CALCULADO (figures) + TEXTO RECUPERADO (context, stripped of figures for numeric intents) + the previous conversation. Since 5 nov the chat is **RAG first** (`_recuperar_primero`): Chroma is searched before interpretation; the retrieved parts are passed to the interpretation as hints, answer by themselves when the plan would only ask for clarification (in-scope question or follow-up, no respondent ID), fill in when the filtered support search finds nothing, and instrument-level questions get the instrument's ficha (`_fichas`); when calculation and retrieved text differ, the calculation wins (prompt rule 15). Follow-ups get the previous turn's topic from `rag_log` (`MensajeHistorial.consultaId`), and «¿qué significa eso?» re-runs the previous plan. Router listings (description, structure, patterns, ungraded tests) and `filtrar_respondentes` are worded by the model with the retrieved text, with the computed listing as fallback; `datos_respondente` is paraphrased above its table; findings list 3–4 patterns. Replies are rejected if empty, if they deny, write a table, invent an ID, change/omit a figure or quote text not in the data (or not in the question it cites). Sources list only what the result used (KPIs only for KPI questions). `rag_log.plan` / `rag_log.tiempos` store the plan and ms per stage. Without a valid plan the rule router below takes over. `POST /rag/interpretar` returns plan + computed result for debugging.
3. **Router** (`services/enrutador.py`): rule-based intent detection (respondent IDs, question numbers, levels, group values from respondent context such as `turno`, KPIs, hardest item, participant + topic). The answer is **computed** with `shared/conocimiento/consultas.py` over the documento vigente (percentages over `respuesta_interpretada` when it has rows). The LLM only words the `RESULTADO CALCULADO`: if it changes a figure (`cifras_fieles`) or denies a computed result, the computed text is returned instead; "does not exist" is answered without the LLM. Only KPI intents add fragments (`mixta`), plus the KPI's verified sources (`kpi_fuente`, cited `[Fuente KPI: …]`).
   - **Filters** (`filtro`: «uno de los estudiantes que sí reprobaron por falta de tiempo», «¿cuántos trabajan más de 30 horas?», «¿quiénes del turno vespertino…?»): conditions are built by rules over the document's own catalog of questions and chosen options (word stems; «sí»/«no» groups every option starting with it; levels; numeric comparisons; several conditions; context groups; an instrument named by title narrows the scope) and counted with `consultas.filtrar`. Actions: count, list IDs, or pick one respondent with all answers and a computed summary. If the rules find no condition, `filtro_llm` asks Ollama for the condition only (JSON, temperature 0, `RAG_FILTRO_LLM`), validated against the catalog; generated SQL is never executed.
   - **Quality** (`calidad`: «¿qué análisis me sugieres…?», «¿qué tan confiable es…?»): cleaning statistics and suggestions from `limpieza_ejecucion`. Definition questions («¿qué significa un alfa bajo?») still go to the glossary.
4. Otherwise **semantic** retrieval from PA: `RAG_MIN_SCORE = 0.65` (no fragment below it enters an answer, not even as filler; a «hallazgo» about a topic nothing in scope reaches 0.65 → "sin información"), at most 1 ficha and 3 fragments per instrument, `top_k ≤ 8`, numbered `[Fuente n]` = n-th source card. Definition questions add the methodological **glossary** (`dominio.yaml → glosario`, cited `[Glosario: …]`). Max similarity below `RAG_FUERA_MAX` (0.30) → out-of-domain message; between that and `RAG_MIN_SCORE` → "sin información". In the gray zone (`RAG_MIN_SCORE ≤ score < RAG_ZONA_GRIS_MAX`) an Ollama classifier (JSON, temperature 0, `RAG_CLASIFICADOR_LLM`, `RAG_CLASIFICADOR_MODELO`) can reject; if Ollama fails the question continues.
4b. **Hybrid search** (`services/hibrida.py`, 11 nov; `RAG_HIBRIDA`, `RAG_MIN_COBERTURA` 0.75, `RAG_LEXICOS_MAX`): Chroma's semantic ranking is fused (RRF, k 60) with a word search over `documento_vectorizado.chunk_texto` (Postgres full text in Spanish to find, BM25 with real document frequencies to rank, instrument-describing sections before per-person ones, ≤ 2 per-person chunks per instrument; GIN index in `migrations/2026_20_busqueda_hibrida.sql`). A chunk reaches the answer if its cosine ≥ `RAG_MIN_SCORE` or it holds ≥ 75 % (and ≥ 2) of the question's content words; the ficha and KPI chunks by meaning only with ≥ 50 % of them. Cards still show the cosine. Off (`RAG_HIBRIDA=false`, also in tests) = semantic only. No reindex needed.
4c. **«Ver métricas»** (`services/metricas_respuesta.py` → `indicadores.{recuperacion, fundamentacion, citas}` in `GET /rag/consultas/{id}/metricas`; `VerMetricas.tsx` under each answer): deterministic, no judge — retrieved chunks with cosine, word coverage, rank in each search and why they passed; sentences supported by a retrieved chunk or the computed result (≥ 50 % of their content words in one context); sentences with citations and citations to non-existent sources; plus the existing figures/IDs with support and stage times.
5. **Prompt** (`services/prompt.py`): PA's 8 rules in the Ollama `system` field (`num_ctx 4096`, `temperature 0.2`) plus: retrieved text goes inside `<datos fuente="n">…</datos>` and is data, never instructions; never identify people; don't recompute the result; cite IDs and questions.
6. **After generation**: drop the stray "sin información" phrase, invented `[Glosario/Ayuda: …]` citations and emails/phones/student IDs. Structured answers are not streamed token by token (they are verified first).
Each query is logged in `rag_log` with `decision_dominio`, `motivo`, `score_max`, `ruta` (`semantica | estructurada | mixta | ayuda`), `instrumentos` and `contexto_usado`.

**Answer cache** (`rag_service.clave_cache`): a fingerprint of the normalized question, scope, vigente version of each instrument, research context, model, `_VERSION_RESPUESTAS` and the prompt rules. An identical query within `RAG_CACHE_HORAS` (24; 0 = off) reuses the stored answer (`rag_log.clave_cache`, `rag_log.salida`) without calling Ollama (`enCache: true`; its metrics are read from the original row). Publishing a new version changes the fingerprint; bump `_VERSION_RESPUESTAS` when you change how answers are computed or worded. Tests disable the cache by default (autouse fixture in `conftest.py`).

**News panel** (`services/noticias.py`, `GET /visualizacion/noticias`): RSS/Atom feeds from `config/noticias.yaml` (verified URLs), plus GNews when `NOTICIAS_API_KEY` is set; deduplicated, newest first, cached `NOTICIAS_CACHE_MIN` minutes; offline it returns the last good list or an empty list with `aviso` (never mock news). The chat scope (`instrumentoIds`; empty = whole approved collection) comes from the selector in `ChatPage` (my research / chosen instruments / whole collection).

**Metrics** (`services/evaluacion.py`): after answering, a single background worker computes RAGAS-style metrics without reference — faithfulness, answer relevancy (3 generated questions, cosine with the embedding model, 0 if evasive) and context precision (`ContextUtilization` average precision) — with a local judge (`RAG_JUEZ_MODELO`, empty = `OLLAMA_MODEL`; disable with `RAG_METRICAS`). **On demand by default** (`RAG_METRICAS_BAJO_DEMANDA`): each reply is stored as `pendiente` and is only judged when the user clicks «Calcular evaluación» (`POST /rag/consultas/{id}/metricas`), because judge (qwen) and writer (llama) don't fit together on a 4 GiB GPU and per-reply judging pushed the next question from ~5 s to ~35 s. Stored in `rag_log.metricas`, `modelo_juez`, `fecha_metricas`; read with `GET /rag/consultas/{id}/metricas` (the chat panel polls it and warns it is an approximate evaluation). Refusals and fixed answers are `omitida`. Computed answers shown as-is are `calculada`: faithfulness 1 by construction, relevancy and context precision still judged against the computed result. Faithfulness retries a miscounted verdict list and falls back to one claim per call; a claim copied from the context (all figures present, ≥75 % of its words in one line) counts as supported (`sustento_literal`); `cifras_sin_sustento` lists figures not in the context, without the judge. Planned answers that fail verification are regenerated once with the reason before falling back (`rag_log.plan.verificacion`). Since 28 oct the panel of each answer has three parts: **system indicators** (`services/indicadores.py`, no judge, computed on read from `rag_log`: intent, whether the answer was written by the model / shown as the computed result / a template, regenerations, figures with support, invented IDs, ms per stage), the **judge** (`POST …/metricas?juez=<model>` evaluates with another judge; every evaluation is stored per judge in `rag_metrica_juez`, the default judge's also in `rag_log.metricas`) and the **human rating** (`PUT /rag/consultas/{id}/calificacion` → `rag_calificacion`, 0 bad / 1 partial / 2 good). The chat selector's «Modelo del servidor» sends no `modelo`, so `OLLAMA_MODEL` drives every stage; redaction temperature is `RAG_TEMPERATURA_REDACCION` (0.2).

**Claude Fable 5.2 judge** (`services/juez_fable.py`, 11 nov; Anthropic SDK `anthropic==2.8.0`, which uses `httpx2` and does not clash with the pinned `httpx`): every evaluable reply (not `omitida`, not a cache copy) is scheduled from `registrar_consulta` and judged in the background through the Anthropic API, so it is not on demand. Six RAGAS 0.4.3 metrics: context precision, context recall, faithfulness, response relevancy (3 questions from the reply only, cosine with the local embedding model), noise sensitivity (relevant mode; lower is better; irrelevant mode in the detail) and factual correctness (F1). The judge returns verdicts only (structured outputs, JSON schema); the scores are computed in Python (`calcular`). Recall, noise and factual correctness compare against a reference answer the judge writes **without seeing the reply**, from the used context plus `RAG_JUEZ_FABLE_AMPLIADO` extra Chroma chunks of the same instruments (no threshold); `detalle.referencia.origen` records it. Stored in `rag_metrica_juez` (`modelo_juez = RAG_JUEZ_FABLE_MODELO`), returned as `juezFable` in `GET /rag/consultas/{id}/metricas`, shown by `EvaluacionFable.tsx` inside «Ver métricas»; `POST …/metricas?juez=claude-fable-5-2` re-runs it. Settings: `ANTHROPIC_API_KEY` (missing → `omitida` with the reason), `RAG_JUEZ_FABLE`, `RAG_JUEZ_FABLE_MODELO`, `RAG_JUEZ_FABLE_ESFUERZO` (`high`), `RAG_JUEZ_FABLE_CONCURRENCIA`. Server-side refusal fallback is on (`fallbacks: "default"`): rows judged by the fallback model carry `fallback: true` and `modelo_real`. Tests turn it off (autouse fixture) and cover it with a fake judge in `tests/test_juez_fable.py`.

**Offline evaluation** (RAGAS 0.4.3 real, isolated: its pyarrow requires NumPy 2 and it needs LangChain 0.3, both incompatible with the services):
```powershell
py -3.12 -m venv .venv-ragas; .venv-ragas\Scripts\python.exe -m pip install -r tools\rag\requirements-ragas.txt
docker compose exec ollama ollama pull nomic-embed-text      # embeddings for RAGAS (no torch on the host)
.venv-ragas\Scripts\python.exe tools\rag\evaluar_ragas.py --ids enc_10=59,pru_01=55,ent_01=60,enc_04=50 [--continuar]
.venv\Scripts\python.exe tools\rag\verificar_chat.py --ids …   # end-to-end check: answer, sources and metrics per case
```
**Model experiment (writer × judge)**: `services/visualization-service/scripts/modelos/` (README there), run inside the container: `generar_casos.py` writes `casos.json` (the researcher's 14 cases / 28 turns over instrument 127, turn types dato/inexistente/interpretativo/capacidad/control, expected figures computed straight from the DB), `juzgar.py --juez <model> --corrida <writer>=<first>-<last rag_log_id>` evaluates a run with one judge, `calificar.py --corrida …` (interactive, no `-T`) rates in the terminal the turns without a human rating, `reporte.py` writes reference metrics, the writer × judge matrix, self-evaluation bias and the judge reliability cross-check (Cohen's kappa, Scott's pi, Spearman vs the human rating) to `storage/evaluacion_modelos/<date>/`. Set `RAG_CACHE_HORAS=0` in `.env` while running it.

`tools/rag/preguntas_referencia.json` holds 20 reference questions with expected answers. The script reports domain-decision accuracy, the service's own metrics, context recall, and RAGAS side by side, saving after each question (`--continuar` resumes). The 3B judge needs `instructor.Mode.JSON_SCHEMA` (patched in the script) or it echoes the schema. `tools/rag/procesar_instrumento.py` runs the 7 wizard steps through the API (used to prepare `enc_10`, the synthetic survey with `turno`).

Embeddings: `paraphrase-multilingual-mpnet-base-v2` (768-dim). The model is cached in the `hf_cache` volume. The analysis image installs CPU-only torch first, which avoids a ~7 GB CUDA download. Keep that ordering in `Dockerfile.analysis-service`.

### Frontend rules (from `pixel-perfect-pixel/AGENTS.md`)
- All data access goes through async functions in `src/api/`, which call the backend through `pedir()` in `src/api/client.ts` (there are no mock data any more). Still client-side: the investigaciones list, kept in localStorage (`src/api/investigaciones.ts`) together with each one's chat session (`indagata.chat.<id>`: context + finished messages), so choosing an investigation in the selector resumes its chat; «Mis investigaciones» on `/investigacion` resumes or deletes them.
- The JWT is stored in localStorage under `indagata.token`. The frontend never calls storage-service directly; downloads go through `/visualizacion/descargas`.
- Code is organized by feature (`src/features/{auth,upload,instruments,research,chat,kpis,...}`), with shared domain types in `src/types/index.ts`. Routing uses TanStack Router file routes in `src/routes/`, with `_panel.tsx` as the authenticated layout. No React Router or Next.js.
- Colors, typography and shadows come only from semantic tokens in `src/styles.css`. Never use literal color classes.

### Database changes
`infrastructure/postgres/init/*.sql` runs **only when the `postgres_data` volume is empty**. Schema changes for an existing DB go in `infrastructure/postgres/migrations/`, which is mounted at `/migrations`. Apply them manually with `docker compose exec postgres psql -U postgres -d indagata_db -f /migrations/<file>.sql`. Then update `01_schema.sql` and the matching `shared/models` + `shared/schemas`.
